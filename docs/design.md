# 4つの尺度 学習ゲーム 設計書

初版: 2026-09-27　第2版: 2026-09-27（授業担当者の確認を反映）　第3版: 2026-09-28（テストプレイの指摘を反映）

## 目的

大学の授業で、学生が任意の項目を見て、それが名義尺度・順序尺度・間隔尺度・比例尺度のどれにあたるかを判断できるようにする。学生はゲームを遊びながら判断の手順を身につけ、最後には時間制限のもとで素早く正確に分類できる状態を目指す。

4つの尺度の区別は Stevens (1946) が示した分類に由来する。日本語では比例尺度を「比率尺度」と書く教材もあるため、アプリ内の用語は「比例尺度」に統一し、尺度の図鑑に別名として「比率尺度」を併記する。

## 対象と利用環境

- 授業は大学でおこなうが、問題の難易度は高校生でも解ける程度にそろえる。
- 学生は各自のスマートフォンまたは PC のブラウザで遊ぶ。
- 教員は URL を配るだけで授業に使えるようにし、ログインやサーバーを必要としない。
- 画面は幅 360px・高さ 640px のスマートフォンで操作できることを最低条件とし、性能の高くない端末でも動くようにする。
- プレイ画面は PC でもスマートフォンでも画面の中央に置き、プレイ中の画面はスクロールせずに1画面に収める。
- ランキングは作らない。個人のプレイ履歴は、復習に使うために各端末に残す。

## 学習の流れ

学生は3つのモードを順に進む。STEP 1 で判断の手順を覚え、STEP 2 で手順を使って一問ずつ確かめ、STEP 3 で手順を意識しなくても素早く判断できるように練習する。モードの順序は推奨として示すが、どのモードからでも始められる。各モードの結果画面には、次のモードへ進むボタンを置く。

### STEP 1 フローチャートモード

1回のプレイで5項目を扱う。アプリは各尺度から1項目ずつと、残り1項目をランダムに選ぶ。発展（level 3）と議論のある項目は出さない。学生は1つの項目について、次の3つの問いに「はい／いいえ」で順に答える。「いいえ」を選んだ時点、または3つとも「はい」と答えた時点で問いは終わり、最後に学生自身が4つの尺度から1つを選ぶ。

| 順 | 問い | 「はい」の例 | 「いいえ」の例 | 「いいえ」なら |
|---|---|---|---|---|
| 1 | 「上・下」や「多い・少ない」で並べられる？ | 部屋の広さ | 好きな動物 | 名義尺度 |
| 2 | ものさしの目盛りのように、1つ分の幅はどこでも同じ？ | 定規で測った長さ | メダルの色 | 順序尺度 |
| 3 | 0 は「何もない」ってこと？「2倍」と言える？ | 小銭の枚数 | IQ | 間隔尺度 |

3つとも「はい」なら比例尺度になる。初学者にとって「値の差が等しい」「絶対的な原点」といった言い方は抽象度が高いため、問いは短い話し言葉にし、各問いに「はい」と「いいえ」の具体例を1行ずつ添える。例とヒントには問題（`data/items.json`）にない事例だけを使う。問題と同じ事例を例に使うと、その問題が出たときに答えを教えることになるためである。`tests/items.test.js` は、問題の項目名が例やヒントに含まれていないことを検査する。問いの文面、例、ヒントは `js/scales.js` の `FLOW_STEPS` と `PICK_HINT` にまとめてある。

画面は、項目カード、問いの枠、メモリンのメッセージの3つだけで構成する。メモリンは、問いごとに項目の例の値を使って考え方を促す（例:「『第1位』と『第2位』、どちらかが上と言えるかな？」）。学生が問いに誤って答えると、メモリンは答えの向きに合わせたヒントを出す。つまり、正しくは「はい」なのに「いいえ」と答えた場合と、その逆の場合とで、別のヒントを示す。同じ問いで2回まちがえると、メモリンは正しい答えを明かす。

最後に尺度を選ぶ場面では、問いの枠に「たどった答え：問い1 はい → 問い2 いいえ」のように経路を示す。学生が誤った尺度を選ぶと、メモリンは1回目に「『いいえ』で止まった問いが決め手」と促し、2回目に正解と、問いと尺度の対応を示す。正解すると、アプリは項目の解説を示す。このモードでは得点をつけず、問いと最後の選択の両方で一度もまちがえなかった項目の数だけを示す。

### STEP 2 4択クイズモード

1回のプレイは10問で、はじめの4問は level 1 から出し、残りに level 2・3 を混ぜる。学生が答えると、アプリは正解の箱を塗りつぶして示し、解説を表示する。誤答の場合は、フローチャートのどの問いで判断が分かれたか（学生の答えならその問いは「はい」、正しくは「いいえ」など）も示す。

議論のある項目（`contested: true`）はこのモードでだけ出題する。学生が別解（`alternatives`）を選んだ場合は「△ その考え方もある」と示し、正解として数える。結果画面では誤答した項目を解説つきで並べ、誤答した項目だけで出題しなおせる。

### STEP 3 60秒仕分けモード

画面の下部に4つの箱を並べ、上部に項目カードを1枚ずつ出す。学生はカードを箱へドラッグするか、箱をタップして仕分ける。キーボードでは 1〜4 キーで選べる。制限時間は60秒で、時間内なら何枚でも仕分けられる。

演出は寿司打を参考にする。正しく仕分けると得点とコンボ（連続正解数）が増え、誤ると減点・コンボ切れ・0.3秒の操作停止が起き、画面に正しい尺度が表示される。終了画面には称号、得点、正解数と回答数、正答率、1分あたりの正解数、平均回答時間、最大コンボ、次の称号の条件、誤答した項目の解説を示す。議論のある項目は時間制限のもとでは不公平になるため出さない。

出題は、まず4つの尺度から1つを均等に選び、次にその尺度の山札から1枚引く。間隔尺度の項目は他の尺度より少ないため、項目から直接選ぶと間隔尺度のカードがほとんど出なくなるからである。同じ項目は続けて出さない。

## 採点と称号（STEP 3）

採点は `js/scoring.js` に純粋な関数として実装し、`tests/logic.test.js` で検査している。以下の数値はすべて初期値であり、授業で試したあとに `SORT_CONFIG` と `TITLES` を書き換えて調整する。

```
正解: (基本点 100 + 速さボーナス) × コンボ倍率
誤答: −50（コンボは 0 に戻る）

速さボーナス = 100 × (6 − 回答秒数) / (6 − 1.5)   ※1.5秒以内は100、6秒以上は0
コンボ倍率   = 1 + 0.1 × min(直前までの連続正解数, 10)
```

合計が負になった場合は 0 点とする。称号は武道の級・段になぞらえ、得点と正答率の両方が基準を満たした称号のうち最も上のものを与える。正答率の下限を設けた理由は、当てずっぽうで大量に仕分けた学生が上位の称号を得ることを防ぐためである。

| 級・段 | 称号 | 得点 | 正答率 |
|---|---|---|---|
| 皆伝 | スティーヴンスの継承者 | 7500 以上 | 95% 以上 |
| 三段 | 尺度の賢者 | 5500 以上 | 90% 以上 |
| 初段 | 比例の魔導士 | 4000 以上 | 85% 以上 |
| 二級 | 間隔の騎士 | 2800 以上 | 80% 以上 |
| 四級 | 順序の旅人 | 1800 以上 | 70% 以上 |
| 六級 | 名義の番人 | 1000 以上 | 60% 以上 |
| 八級 | 目盛り見習い | 400 以上 | 40% 以上 |
| 十級 | ものさし拾い | それ未満 | — |

得点の基準は、全問正解した場合の試算から決めた。1枚2秒のペースなら約10300点、2.5秒なら約7600点、3秒なら約5800点、4秒なら約3500点、6秒なら約1450点になる。皆伝は1枚2.5秒以内でほぼ全問を正解する学生を想定している。

称号ごとに短い説明文（`TITLES` の `desc`）を付けた。仕分けの結果画面と開始画面から「称号と階級」の説明画面（`js/modes/titles.js`）を開ける。説明画面は8つの称号を上から並べ、各称号を開くと条件と説明文を示す。結果画面から開いた場合は、そのとき得た称号を枠で囲んで開いた状態にし、「結果にもどる」で結果画面に戻る。戻るときは記録を保存しなおさない。画面に収めるため、称号は1つ開くとほかが閉じる。得点の計算方法も、同じ画面の開閉できる欄で説明する。

## プレイ履歴と復習

アプリは各モードの1プレイごとに、日時、モード、成績、項目ごとの回答（選んだ尺度、正誤、仕分けでは回答秒数）をブラウザの localStorage に保存する。保存は最新300プレイまでとし、それを超えると古いものから消す。処理は `js/history.js` にまとめている。

「冒険の記録」画面では、プレイ回数、仕分けの自己ベストと称号、最近20件のプレイ、苦手な項目を示す。苦手な項目は、まちがえた回数の多い順に最大10件を並べ、最後に選んだ誤答と解説を添える。学生は苦手な項目だけで4択クイズを解きなおせる。

localStorage の記録は端末とブラウザごとに残るため、別の端末とは共有されず、ブラウザのデータを消すと記録も消える。この制約を補うため、記録を CSV（1回答1行、Excel で開ける BOM 付き UTF-8）で保存するボタンを置いた。学生がこの CSV を課題として提出することもできる。

## 画面の意匠とアクセシビリティ

画面は昔の家庭用 RPG を思わせる意匠にする。暗い紺の背景に白い二重枠のウインドウを置き、選択中の項目には点滅する「▶」のカーソルを付け、マスコットのメモリン（ものさしの妖精）がメッセージウインドウで話しかける。特定のゲームの画像や名称は使わず、意匠は独自に作る。

性能の高くない端末でも動くよう、次の方針をとる。

- 外部ライブラリと画像ファイルを使わず、マスコットのドット絵は 12×16 マスの SVG で描く。
- 影のぼかし、半透明の重ね合わせ、常時動くアニメーションを使わない。動きは点滅とカードのゆれだけにする。
- 画面の高さを抑えるため、結果画面の誤答一覧や冒険の記録の解説は、開閉できる欄に入れる。尺度の図鑑はタブで1つずつ表示する。
- 仕分けモードの残り時間は 0.1 秒ごとに1回だけ更新する。

色覚の多様性と読みの困難に配慮して、次の方針をとる。

- 尺度の色は、名義 #dd55ff（紫）、順序 #77ffff（水色）、間隔 #ffff00（黄）、比例 #ff5555（赤）とする。この4色は、1型・2型・3型の色覚をシミュレーション（Machado et al. 2009）した場合も含め、どの2色の組み合わせでも色差（CIELAB の ΔE）が 48 以上離れるものを探索して選んだ。第2版の配色は、1型色覚で名義と順序が ΔE 12、2型色覚で間隔と比例が ΔE 17 まで近づき、見分けにくかったため改めた。4色とも背景に対するコントラスト比は 5.5:1 以上である。
- 尺度には必ず形の記号（名義 ●、順序 ▲、間隔 ■、比例 ★）と名前を併記する。色が見分けられなくても尺度を区別できる。
- 正誤、カーソル、残り時間の表示には尺度の4色を使わず、白と記号で示す。尺度の色と意味が混ざらないようにするためである。
- 正誤は色ではなく「○ 正解」「× 残念」「△」の記号と文字で示す。
- 本文は UD フォント（BIZ UDPゴシック）で表示し、行間と字間を広めにとる。ドット文字（DotGothic16）は見出しとメニューだけに使い、設定で UD フォントに切り替えられる。
- 本文はひらがなだけで書かず、漢字かな交じりで書く。レトロゲームにならってひらがなを多用すると、語の切れ目が分かりにくくなるためである。
- 設定で、文字の大きさ、メッセージの表示速度（1文字ずつ表示するか、すぐ全文を出すか）、点滅・ゆれの有無を変えられる。OS で動きを減らす設定をしている場合も、点滅とゆれを止める。
- 設定の「画面の色」で、モノクロ4階調に切り替えられる。色は、ニンテンドー3DS のバーチャルコンソールでゲームボーイ作品を表示するときの、わずかに黄みがかったグレー4色（RGB 200,200,168／160,160,136／104,104,80／40,40,24）に合わせた。このモードでは、文字にいちばん暗い色だけを使い、明るい2色の背景に対してコントラスト比 5.6:1 以上を確保する。2番目に暗い色は、文字に使うとコントラストが 3.3:1 以下になるため、ウインドウの内枠とマスコットの陰にだけ使う。尺度は色で区別できなくなるが、形の記号と名前で見分けられる。`tests/colors.test.js` がこの条件を検査する。
- 1文字ずつ表示するメッセージは、画面読み上げソフト向けに全文を別に持つ。すべての操作はキーボードでもおこなえる。

## 問題データの仕様

問題項目は `data/items.json` に置く。第2版は57項目で、内訳は名義16、順序16（うち議論あり1）、間隔8（うち議論あり1）、比例17である。第2版では、じゃんけんの手、ガチャのレアリティ、おみくじ、ラーメン店の辛さの段階、スコヴィル値、RPG の HP、サウナの室温など、身近で意外性のある項目を加えた。項目を増やす作業は、教員がこのファイルを直接編集しておこなう。

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 一意の識別子。尺度の頭文字＋連番（議論のある項目は c） |
| `label` | ○ | カードに表示する項目名 |
| `example` | ○ | 値の例。項目名だけでは測り方が決まらない場合の手がかりになる |
| `scale` | ○ | 正解の尺度（`nominal` / `ordinal` / `interval` / `ratio`） |
| `level` | ○ | 1 = 基本、2 = 数字だが名義・順序になる引っかけや身近な変わり種、3 = 発展 |
| `explanation` | ○ | 解説。なぜその尺度になるかを、フローチャートの問いに沿って書く |
| `contested` |  | 分類に議論がある場合 `true`。フローチャートと仕分けでは出題しない |
| `alternatives` |  | 議論のある項目で、正解に準じて認める尺度 |

同じ対象でも測り方によって尺度が変わるため、`label` には単位や測り方を書き、`example` に具体的な値を示す。たとえば温度は摂氏なら間隔尺度、絶対温度なら比例尺度になり、辛さは「1辛・2辛」なら順序尺度、スコヴィル値なら比例尺度になる。`npm test` を実行すると、必須フィールドの欠け、重複、各尺度の出題数不足を検出できる。

## 技術構成

アプリはビルドを必要としない静的な Web ページとして作り、GitHub Pages で公開する。画面の切り替え、採点、履歴の保存はすべて学生のブラウザの中で JavaScript が実行するので、ゲームとして動的に動いてもサーバーは要らない。

HTML・CSS・JavaScript（ES Modules）だけで構成し、外部ライブラリは使わない。フォントだけは Google Fonts から読み込み、読み込めない環境では端末に入っているゴシック体で表示する。ドラッグ操作は Pointer Events で実装し、マウスとタッチを同じコードで扱う。

開発時の確認方法は次のとおりである。`fetch` で JSON を読み込むため、index.html をファイルとして直接開くと動かない。

```
npm start   # python3 -m http.server 8000 で http://localhost:8000 を開く
npm test    # Node.js 標準のテストランナーで、問題データとロジックを検査する
```

```

```
