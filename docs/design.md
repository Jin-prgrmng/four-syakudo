# 4つの尺度 学習ゲーム 設計書（初版）

作成日: 2026-09-27

## 目的

高校の情報科・数学科の授業で、生徒が任意の項目を見て、それが名義尺度・順序尺度・間隔尺度・比例尺度のどれにあたるかを判断できるようにする。生徒はゲームを遊びながら判断の手順を身につけ、最後には時間制限のもとで素早く正確に分類できる状態を目指す。

4つの尺度の区別は Stevens (1946) が示した分類に由来する。日本語では比例尺度を「比率尺度」と書く教材もあるため、アプリ内の用語は「比例尺度」に統一したうえで、解説画面に別名として「比率尺度」を併記する。なお、情報Ⅰの教科書や文部科学省の教員研修用教材でどちらの表記が使われているかは、教材本文を確認できていないため未確認である。

## 対象と利用環境

- 対象者は高校生とし、用語は平易にして、題材は日常生活と学校生活から選ぶ。
- 生徒は各自のスマートフォンまたは PC のブラウザで遊ぶ。
- 教員は URL を配るだけで授業に使えるようにし、ログインやサーバーを必要としない。
- 画面は幅 360px のスマートフォンで操作できることを最低条件とする。

## 学習の流れ

生徒は3つのモードを順に進む。STEP 1 で判断の手順を覚え、STEP 2 で手順を使って一問ずつ確かめ、STEP 3 で手順を意識しなくても素早く判断できるように練習する。モードの順序は推奨として示すが、どのモードからでも始められるようにする（ロックの要否は未決事項に記す）。

### STEP 1 フローチャートモード

生徒は1つの項目について、次の3つの問いに「はい／いいえ」で順に答える。途中で「いいえ」を選んだ時点で尺度が決まる。

| 順 | 問い | 「いいえ」なら |
|---|---|---|
| 1 | 値を小さい順・大きい順に並べることに意味はあるか | 名義尺度 |
| 2 | 値と値の差（間隔）は、どこでも同じ大きさを表しているか | 順序尺度 |
| 3 | 0 は「まったくない」ことを表し、「2倍」「半分」と言えるか | 間隔尺度 |

3つとも「はい」なら比例尺度になる。生徒が問いに誤って答えた場合、アプリはその問いの位置で止めて、項目に即したヒントを示してから答え直させる。このモードでは得点をつけず、手順を最後までたどることを優先する。問いの文面とヒントは `js/scales.js` の `FLOW_STEPS` に置く。

### STEP 2 4択クイズモード

アプリは項目を1枚ずつ示し、生徒は4つの尺度から1つを選ぶ。生徒が答えると、アプリは正誤と解説（`explanation`）を示し、誤答の場合はフローチャートのどの問いで判断を誤ったかも示す。1回のプレイは10問とし、終了時に正答数と、誤答した項目の一覧を示す。出題は level 1 から始め、正答が続いたら level 2・3 の項目を混ぜる。

分類に議論のある項目（`contested: true`）はこのモードで出題し、正解に加えて別解（`alternatives`）を選んだ場合は「その考え方もある」と示して部分的に正解とする。

### STEP 3 60秒仕分けモード

画面の下部に4つの箱（名義・順序・間隔・比例）を並べ、上部に項目カードを1枚ずつ出す。生徒はカードを箱へドラッグするか、箱をタップして仕分ける。スマートフォンではドラッグよりタップのほうが速く確実なため、両方の操作を受け付ける。制限時間は60秒とし、時間内に何枚でも仕分けられる。

演出は寿司打を参考にする。寿司打では流れてくる皿をタイピングで取り、終了時に得点と判定を示す。このアプリでは、カードを正しく仕分けると得点と連続正解数（コンボ）が増え、誤ると減点とコンボの途切れが起きる。終了画面には得点、正答率、1分あたり正答数、平均回答時間、最大コンボ、判定を示す。議論のある項目は時間制限のもとでは不公平になるため出題しない。

## 採点の仕様（STEP 3）

採点は `js/scoring.js` に純粋な関数として実装済みであり、`tests/logic.test.js` で検査している。以下の数値はすべて初期値であり、授業で試したあとに `SORT_CONFIG` と `RANKS` を書き換えて調整する。

1枚ごとの得点は次の式で計算する。

```
正解: (基本点 100 + 速さボーナス) × コンボ倍率
誤答: −50（コンボは 0 に戻る）

速さボーナス = 100 × (6 − 回答秒数) / (6 − 1.5)   ※1.5秒以内は100、6秒以上は0
コンボ倍率   = 1 + 0.1 × min(直前までの連続正解数, 10)
```

合計が負になった場合は 0 点とする。判定は、得点と正答率の両方が基準を満たした段階のうち最も上の段階とする。正答率の下限を設けた理由は、当てずっぽうで大量に仕分けた生徒が上位の判定を得ることを防ぐためである。

| 判定 | 称号 | 得点 | 正答率 |
|---|---|---|---|
| S | 尺度マスター | 6000 以上 | 90% 以上 |
| A | 尺度の達人 | 4000 以上 | 80% 以上 |
| B | 一人前 | 2500 以上 | 70% 以上 |
| C | 見習い | 1200 以上 | 50% 以上 |
| D | もう一度フローチャートへ | それ未満 | — |

得点の基準は、全問正解した場合の試算から決めた。1枚2.5秒で24枚を仕分けると約7600点、4秒で15枚なら約3500点、6秒で10枚なら約1450点になる。つまり、S は1枚あたり3秒前後でほぼ全問を正解する生徒を想定し、C は1枚6秒程度で着実に正解する生徒を想定している。

生徒の自己ベストはブラウザの localStorage に保存する。localStorage は端末ごとに保存されるため、クラス全体のランキングは作れない（未決事項を参照）。

## 問題データの仕様

問題項目は `data/items.json` に置く。初版は40項目で、内訳は名義12、順序11（うち議論あり1）、間隔6（うち議論あり1）、比例11である。項目を増やす作業は、教員がこのファイルを直接編集しておこなう。

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 一意の識別子。尺度の頭文字＋連番（議論のある項目は c） |
| `label` | ○ | カードに表示する項目名 |
| `example` | ○ | 値の例。項目名だけでは測り方が決まらない場合の手がかりになる |
| `scale` | ○ | 正解の尺度（`nominal` / `ordinal` / `interval` / `ratio`） |
| `level` | ○ | 1 = 基本、2 = 数字だが名義・順序になる引っかけなど、3 = 発展 |
| `explanation` | ○ | 解説。なぜその尺度になるかを、フローチャートの問いに沿って書く |
| `contested` |  | 分類に議論がある場合 `true`。仕分けモードでは出題しない |
| `alternatives` |  | 議論のある項目で、正解に準じて認める尺度 |

項目を作るときは、同じ対象でも測り方によって尺度が変わる点に注意する。たとえば温度は、摂氏なら間隔尺度、絶対温度なら比例尺度になる。このため `label` には単位や測り方を書き、`example` に具体的な値を示す。`npm test` を実行すると、必須フィールドの欠け、重複、各尺度の出題数不足を検出できる。

間隔尺度に当てはまる身近な項目は他の尺度より少ない。仕分けモードで間隔尺度のカードが偏って少なくならないよう、出題時は尺度ごとに均等に抽選する。

## 技術構成

アプリはビルドを必要としない静的な Web ページとして作る。HTML・CSS・JavaScript（ES Modules）だけで構成し、外部ライブラリは使わない。この構成を選んだ理由は、GitHub Pages にそのまま置けば生徒に URL を配るだけで使え、教員がのちに問題データや数値を直接編集しやすいからである。

ドラッグ操作は Pointer Events で実装し、マウスとタッチを同じコードで扱う。ダークモードには `prefers-color-scheme` で対応する。尺度ごとの色は CSS 変数（`--nominal` など）で定義し、箱・解説・結果画面で共通に使う。

開発時の確認方法は次のとおりである。`fetch` で JSON を読み込むため、index.html をファイルとして直接開くと動かない点に注意する。

```
npm start   # python3 -m http.server 8000 で http://localhost:8000 を開く
npm test    # Node.js 標準のテストランナーで、問題データと採点ロジックを検査する
```

## ディレクトリ構成

```
index.html          入口（モード選択画面）
css/style.css       見た目
js/main.js          画面の切り替え
js/scales.js        尺度の定義とフローチャートの判定（実装済み）
js/scoring.js       仕分けモードの採点と判定（実装済み）
js/modes/           各モードの画面（これから実装）
data/items.json     問題項目
tests/              データとロジックの検査
docs/design.md      この設計書
```

## 開発の段取り

1. 準備（本コミット）: 設計書、問題データ初稿、判定・採点ロジック、画面の雛形、テスト。
2. STEP 1 フローチャートモードを実装する。
3. STEP 2 4択クイズモードを実装する。
4. STEP 3 仕分けモードを実装し、採点ロジックを画面につなぐ。
5. GitHub Pages で公開し、授業前に数名で試して採点の数値と問題の難易度を調整する。

## 未決事項

次の点は授業の運用に関わるため、教員の判断を待って決める。

- 問題項目の妥当性の確認: 初稿の40項目、とくに level 3 の項目と、議論のある2項目（テストの点数、5段階の回答）の扱いを教員が確認する。
- モードのロック: STEP 1 を終えるまで STEP 3 を遊べないようにするかどうか。
- クラス内ランキング: 必要ならサーバーまたは外部サービスが要り、生徒の名前の扱いも決める必要がある。不要なら端末ごとの自己ベストだけにする。
- 結果の提出: 終了画面をスクリーンショットで提出させるか、結果をコピーできる文字列として出すか。
- 制限時間: 60秒で固定するか、30秒・90秒などのコースを選べるようにするか（寿司打のコース選択に相当）。
